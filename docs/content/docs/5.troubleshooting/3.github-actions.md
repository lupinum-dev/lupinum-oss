Open the exact workflow run and find the first failing job. Later failures can
be consequences of that job.

## Job waits for a runner

“Waiting for a runner to pick up this job” is normally GitHub-hosted runner
capacity. It is not the dependency quarantine. Wait for the status to change.
Check GitHub service status when the wait is unusually long.

## Workflow cannot create a pull request

Confirm the job has the required `contents` and `pull-requests` permissions.
Then confirm the organization setting **Allow GitHub Actions to create and
approve pull requests** is enabled. Branch protection still applies.

## Deployment approval is missing

Confirm the job declares `environment: npm`. Confirm that the environment
allows `main` and has a required reviewer. A maintainer cannot approve their
own deployment when the selected protection rule forbids it.

## A third-party service is stale

Confirm the GitHub App has repository access. Check whether CodeRabbit,
Renovate, Vercel, or pkg.pr.new reports the current pull request SHA. Rerun only
after the integration is authorized for the repository.

## A downloaded artifact path is missing

`actions/download-artifact` extracts the uploaded archive into the configured
destination. A common uploaded root can disappear during extraction. Do not
guess that the original local directory still exists below the destination.

Inspect the downloaded tree in the failing job. Make the upload root and the
expected downloaded files explicit. Add a workflow-policy test that uses the
same flat or nested layout before release logic depends on the path.

## A workflow fix does not affect a rerun

A rerun uses the workflow definition from the original run. After a workflow
fix reaches `main`, start a new dispatch. Do not expect “rerun failed jobs” to
load the corrected file.

## A historical release tag returns HTTP 403

GitHub can reject a workflow token that creates a tag at an older commit even
when the job has `contents: write`. The Git reference API can require workflow
write authority for some reference changes. `GITHUB_TOKEN` does not provide a
workflow-write permission.

Do not add a personal access token and do not weaken the release-tag ruleset.
Start reconciliation with the same reviewed version, or without input when the
repository has Automatic Reconciliation. It must verify provenance, registry
integrity, retained CI evidence, changelog intent, and tag absence.

If the workflow reports `HUMAN-ONLY`, run its exact lightweight-tag command.
Confirm that the new tag resolves to the reported source SHA. Rerun only the
failed GitHub Release job. Verify that the GitHub asset and npm tarball have the
same bytes.

## A chained workflow does not start

GitHub does not start a fourth level in a `workflow_run` chain. A main CI run
that starts a version workflow, which dispatches generated-branch CI, cannot
rely on another `workflow_run` to report the result.

Keep the trusted result bridge in the dispatched CI workflow. Give check write
permission only to a separate job that does not check out, install, or run
repository code. Make it depend on the successful aggregate gate. Before it
writes the required check, confirm the generated branch, the single open pull
request, and the exact verified commit.

## A job after the aggregate gate skips

GitHub can propagate an expected skipped lane through a successful aggregate
job. A later dependent job can then skip before its own condition runs.

Use `always()` on the later job and require the aggregate result to equal
`success`. Keep the event and branch restrictions in the same condition. Test
the complete condition as workflow policy.

## A version pull request keeps its Changeset

`git add --intent-to-add .` stages deletions of tracked files. A later plain
`git diff` reads only unstaged changes, so an inert version patch can omit the
Changeset file that the version command deleted. The generated pull request then
keeps old release intent and can propose the same release again.

When intent-to-add is needed to include new files, create and test the patch with
`git diff HEAD`. Add a workflow-policy test that confirms the patch command and
its no-change check both compare with `HEAD`.

## A Node runtime warning appears

An action can target a deprecated internal Node runtime even when the workflow
uses a current Node version. Update the action to a current reviewed commit SHA.
Do not change the package runtime only to hide an action warning.

## pnpm 11 fails in a Node.js 20 lane

pnpm 11 requires Node.js 22 or later. This does not mean that the library must
drop Node.js 20 support. Enable the official standalone mode in
`pnpm/action-setup`, then run the package compatibility test on Node.js 20.

Do not downgrade pnpm only for this lane. An older pnpm version can ignore the
workspace's current dependency-security settings.
