---
title: npm trusted publishing
description: Diagnose OIDC permission denied, missing trust records, and first-package limitations.

---

An npm `E403 OIDC permission denied` error means the workflow identity does not
match a trusted publisher with publish permission.

## Check the exact identity

Compare all four values:

- GitHub repository, such as `lupinum-dev/project`,
- exact maintained workflow file name,
- GitHub environment, which is `npm`, and
- permission, which must allow direct publication.

The file name is part of the identity. A trust record for `release.yml` does
not authorize `publish.yml`. New starters use `publish.yml`. Existing proven
workflows do not need a cosmetic rename.

List the current record:

```bash
npm trust list @lupinum/package-name --json
```

Revoke an incorrect record by its ID. Create the correct record with
`npm trust github ... --allow-publish`.

`E409` normally means a trust record already exists. List and inspect it before
you revoke anything. A direct publisher can appear as `createPackage` in JSON.
The staged-only permission is `createStagedPackage`.

## Recognize first-package behavior

`npm trust github` returns `E404` when the package does not exist. npm staged
publishing also cannot create a new package. Use the documented first npm
bootstrap. Configure trust immediately after the exact certified tarball is
public.

## Check the workflow

The publication job needs `id-token: write`. It must use the protected `npm`
environment and run from the authorized branch. Do not add `NPM_TOKEN` as a
fallback.

After correction, start a new workflow dispatch from updated `main`. Rerunning
an old run uses the old workflow definition.

If the version already exists, do not publish it again. A recovery workflow
must compare the registry bytes with the retained artifact and finish the same
version only when they match.

## Wait for npm processing

npm can accept a publication before its malware scan makes the package visible
to normal registry reads. This can take several minutes. A workflow must poll
for bounded time and report that npm is still processing the package. Temporary
invisibility is not proof that publication failed.

When a prerelease is the only package version, npm can also retain `latest`
while `next` points to the same version. Removing the sole `latest` tag can
return `E400`. Verify `next`; do not churn versions only to remove the automatic
tag.
