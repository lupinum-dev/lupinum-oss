title: Vercel deployment
description: Fix documentation Root Directory, workspace install, and cold-build failures.

---

Use `docs/` as the Vercel Root Directory for library documentation. Use the
repository root for a deployed application.

## Workspace package is missing

A docs app can import packages from its parent workspace. Enable source files
outside the Root Directory. Keep `vercel.json` in `docs/`. Use a parent command
such as `pnpm --dir .. docs:build` so one root script builds required packages
before Nuxt builds docs.

Test from a clean checkout without local `dist/`, `.nuxt/`, or `node_modules/`.

## A library preview is needed

Automatic branch previews are disabled for library documentation because every
push can otherwise consume Vercel build minutes.

Comment exactly `/vercel` on the pull request. The command works for users with
write, maintain, or admin access on same-repository branches. Organization
membership without write access is not enough. Fork pull requests are rejected.
The workflow never checks out or executes pull-request code while it holds the
Vercel token.

The workflow first comments that the preview is starting, then links to Vercel
build details, and finally adds the preview URL or failure result. It also adds
a `Vercel Preview` check to the exact commit. Confirm that the repository has a
project-scoped `VERCEL_TOKEN` secret and the `VERCEL_ORG_ID` and
`VERCEL_PROJECT_ID` variables.

When the ignored build step finds no changes that affect the documentation
site, the workflow first reuses a ready deployment for the exact commit when
one exists. This returns the preview URL without rebuilding. Otherwise it
reports a neutral “preview was not needed” result. This is not a deployment
failure.

Applications can keep automatic Vercel previews when that feedback is worth the
cost. Do not apply the library policy blindly to customer-facing applications.

## Build usage is too high

First check how many deployments ran. A high commit rate can cost more than a
slow build because Vercel builds every relevant push.

Use an `ignoreCommand` that compares `$VERCEL_GIT_PREVIOUS_SHA` with `HEAD` and
lists only files that can affect the site. The command must return `0` when no
relevant file changed, which tells Vercel to skip the build. It must return `1`
when a relevant file changed or the previous SHA is missing, which tells Vercel
to build.

Test the previous commit with `git cat-file` before the diff. A version branch
or another force update can remove Vercel's stored baseline from the checkout.
If the object is unavailable, return `1` without printing a fatal Git error.

Vercel limits `ignoreCommand` to 256 characters. Put the logic in a committed
script when an inline command would exceed that limit. Keep the configured
command short, and run the script from a repository policy test with both a
missing baseline and `HEAD`.

Do not use `HEAD^`. It can miss an earlier relevant commit in the same push.
For libraries, enable Git deployments only for `main` and do not require a
Vercel preview check on pull requests.

Verify the rule with both relevant and unrelated changes. Then confirm in
Vercel that an unrelated deployment is canceled and a relevant deployment
builds. Select the fixed Standard build machine and disable on-demand
concurrency. Do not use Elastic machine selection: a Standard-sized machine
assigned by Elastic is still billed by CPU minute. Re-enable billable machine
selection only when measurements show that faster preview queues have business
value.

## Corepack is unavailable

Vercel can require `ENABLE_EXPERIMENTAL_COREPACK=1` for an older project image
or configuration. Prefer a current runtime that supports the repository's
`packageManager` field and an explicit install command. Use the environment
flag only when current Vercel behavior requires it. Do not copy it to every
project without evidence.

## Generated Nuxt config is missing

If `.nuxt/tsconfig.json` is missing, ensure `nuxt prepare` runs before
type-checking. Delete only generated `.nuxt` state when diagnosing stale output.
Do not remove the required Vercel check.

## Domain fails after a green build

Confirm the production deployment, domain assignment, DNS, and protection
settings. A preview can be green while the canonical domain points to an old,
protected, or failed deployment.

If the page HTML loads but navigation, search, or feedback does not work,
inspect the browser requests for missing `/_nuxt/` assets. Delete only generated
build output and build again. The standard documentation build must verify that
every Nuxt asset referenced by generated HTML exists before deployment.
