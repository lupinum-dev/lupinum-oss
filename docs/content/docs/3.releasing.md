Releases use [Changesets](https://github.com/changesets/changesets). The
maintainer does two things: merge the **Version packages** pull request, then
approve the publish.

## The flow

1. Every pull request that changes published behavior adds a changeset
   (`pnpm changeset`). Agents do this as part of the change.
2. After merge, `release.yml` keeps one open **Version packages** pull request
   up to date. It contains the new versions and the generated `CHANGELOG.md`.
3. **Click 1:** merge the Version packages pull request. Look at its diff
   first: it should change only versions, `CHANGELOG.md` files and
   `.changeset/`. Anything else means stop: close it and find out what pushed
   it.
4. `release.yml` builds and packs every package whose new version is not on npm
   yet. This job has no secrets.
5. **Click 2:** approve the deployment to the `npm` environment in the Actions
   run.
6. The publish job downloads the packed tarballs and runs
   `npm publish <tgz> --provenance --access public --ignore-scripts`. It does
   not check out the repository and does not install anything, so no
   dependency code runs while it can publish. Authentication is npm trusted
   publishing (OIDC); there is no token.
7. The last job creates the Git tag and a GitHub release with the changelog
   section.

To not release, leave the Version packages pull request open. To reject a
release after merging, reject the deployment; nothing is published. The
unpublished version is offered again by the next push to `main` that has no
pending changesets, or at once when you run `release.yml` by hand (**Actions →
release → Run workflow** on `main`).

`release.yml` finds packages through `pnpm-workspace.yaml`. Fixed-version
package sets use a Changesets `fixed` group, so all packages in the set share
one version, one `vX.Y.Z` tag and one GitHub release. Packages that version
independently get one `name@X.Y.Z` tag and GitHub release each.

## Writing a changeset

One line that a user of the library can understand. Present tense. Start with
**Fix**, **Add**, **Remove** or **Change**.

```md
---
'@lupinum/example': minor
---

Add a `delay` option to `useTour()`.
```

A breaking change (a `major` bump, or any breaking change before 1.0) adds a
`Migration:` line:

```md
---
'@lupinum/example': major
---

Remove the deprecated `useLegacyTour()` composable.

Migration: replace `useLegacyTour()` with `useTour()`.
```

CI lints new changesets. When published code changed, CI also runs
`changeset status --since=origin/main`, which fails if no changeset exists.
For a change users cannot notice (tests, internal refactors), add an empty one
with `pnpm changeset --empty`.

## Previews

`preview.yml` publishes every pull request to
[pkg.pr.new](https://pkg.pr.new) and comments install commands. It runs only for
branches in the repository, not for forks. Use it to try a change in a real
project before release.

## Prereleases

```bash
pnpm changeset pre enter next   # following Version packages PRs produce x.y.z-next.n
pnpm changeset pre exit         # back to stable versions
```

Commit the command's change through a normal pull request. Versions that
contain `-` publish under the `next` dist-tag, and their GitHub release is
marked as a prerelease. Stable versions publish under `latest`.

## Hotfix

A hotfix is a normal release: a pull request with the fix and a `patch`
changeset, then the two clicks. Our own code has no waiting period. Only new
third-party dependency versions wait 24 hours; see
[Dependencies](/docs/dependencies).

We fix the latest major only, as `SECURITY.md` says. If an older major needs a
fix anyway, record a decision in `DECISIONS.md`, branch from its last tag, and
change that branch's `release.yml` to run on that branch and to publish
with a dist-tag such as `v1-latest` instead of `latest`. Add the branch to the `npm` environment's
deployment branches for the duration, and remove it afterwards.

## First publication of a new package

npm can only attach a trusted publisher to a package that exists, so the very
first version of a package is published by hand. That version has no
provenance. Every later version does.

The run that packs it is the first push to `main` for a new repository (the
starting version, such as `0.1.0`, is not on npm yet), or the merge of the
Version packages pull request that adds a package to an existing repository.

1. Reject the `npm` deployment of that run.
2. Download its `release` artifact and publish only the tarballs of packages
   that do not exist on npm yet, with your 2FA code:

   ```bash
   gh run download RUN_ID --repo OWNER/REPO --name release --dir release
   npm publish release/PACKAGE.tgz --access public --ignore-scripts --tag latest
   ```

   Use `--tag next` if the first version is a prerelease.
3. Configure trusted publishing and publishing access for the new package as in
   [Set up a repository](/docs/set-up-a-repository#npm-settings).
4. If the artifact also held packages that already existed on npm, run
   `release.yml` by hand on `main` (**Run workflow**) and approve the
   deployment. It skips the version you published, publishes the others with
   provenance and creates the tag and GitHub release. If every package was
   new, create the release by hand from the artifact, with the commit that run
   built (repeat with `.[1]` and so on if `releases.json` has more entries):

   ```bash
   gh release create "$(jq -r '.[0].tag' release/releases.json)" --repo OWNER/REPO \
     --target COMMIT_SHA --notes "$(jq -r '.[0].notes' release/releases.json)"
   ```

Publish the CI-built tarball, not a local build, so the bytes still come from
CI.

## When publishing fails

Read the first failing step. Then:

| Situation | What to do |
|---|---|
| Pack job failed | Nothing was published. Fix the cause in a pull request. After merge, `release.yml` packs the versions that are not on npm yet. You can also start it by hand on `main` (**Run workflow**). |
| `E403`/`E404` from `npm publish` with OIDC | The trusted publisher does not match. Fix it on [npmjs.com](https://www.npmjs.com) (see [Troubleshooting](/docs/troubleshooting#npm-trusted-publishing)), then **Re-run failed jobs**. |
| Some packages published, some not | **Re-run failed jobs.** The publish job skips versions that are already on npm. |
| "cannot publish over the previously published version" | npm versions are immutable. Add a new changeset and release the next version. |
| npm published, tag or GitHub release failed | **Re-run failed jobs.** It skips a release that already exists. Or create it by hand with `gh release create` as in [First publication](#first-publication-of-a-new-package). |
| A published version is broken | Release a fix. Mark the bad version: `npm deprecate @lupinum/example@1.2.3 "Broken, use 1.2.4"`. If needed, point `latest` back: `npm dist-tag add @lupinum/example@1.2.2 latest`. Do not unpublish unless it is a security or legal problem. |

A re-run uses the workflow file from the original run. If you changed
`release.yml` itself, merge the change and let a new run start.

Never add a token, publish a local build, or turn off a required check to get
a release out.
