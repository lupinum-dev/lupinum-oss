---
title: Roll out a fleet standard
description: Change one Lupinum library policy and apply it through reviewed repository pull requests.
icon: lucide:git-pull-request-create
---

Use this procedure when a proven operational lesson changes more than one
library repository.

## Establish the change

Open a focused Lupinum OSS proposal. State the proven problem, repositories in
scope, acceptance criteria, migration cost, and rollback. Correct the handbook
and canonical asset first. Do not begin by editing every repository.

Run `pnpm verify`. When a shared asset changed, run `pnpm shared:sync` and
review every generated copy. The canonical source and generated copies must be
byte-for-byte equal.

## Audit before mutation

Run `pnpm fleet:audit`. This command reads the GitHub default branches, workflow
copy, deployment policy, required checks, and required secret and variable
names. It does not read secret values or change repositories.

Use the Lupinum OSS skill with an authenticated Vercel connection to inspect
the mapped projects. Verify the Git repository, Root Directory, source files
outside the Root Directory, production branch, fixed Standard selection, and
disabled on-demand concurrency. Classify unavailable evidence as unverified.

## Prove the behavior once

When runtime deployment behavior changed, use the one canary marked in
`fleet/libraries.json`. A relevant pull request must create no automatic Vercel
deployment. Comment `/vercel` and prove the exact commit reaches `READY` with a
preview link and build-details link. Repeat the command and prove a ready exact
commit is reused. Prove an unrelated change reports a neutral skip.

Do not create live canary builds in every repository. Static and external-state
audits cover the rest of the fleet.

## Roll out through pull requests

Open one focused pull request per drifting repository. Preserve its local build
command, package layout, and documentation dependency boundary. Apply only the
shared policy and settings that the audit proved are wrong.

Run each repository's own verification command. Read back every GitHub and
Vercel setting after mutation. Merge through normal protection, then run the
fleet audit again. A rollout is complete only when every item is proven or has
an explicit human-only or unverified owner.
