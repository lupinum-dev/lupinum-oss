description: Release a stable package from one certified artifact through the protected workflow.

Use the repository's release workflow after the first npm bootstrap.

## Prepare the change

Use Conventional Commits where the repository requires them. Record release
intent with the repository's selected profile:

- a single-package library uses a reviewed release note and Changelogen;
- a fixed-version package set uses Changesets; and
- an independent package family uses its documented package-family process.

Update public documentation in the same pull request. Run `pnpm verify` before
handoff.

## Prepare the version

Use the repository's protected version process. A single-package repository
can use Changelogen to update its version and `CHANGELOG.md`. A fixed-version
package set uses Changesets to update every package version and package
changelog. An independent package family follows its local compatibility and
version rules.

The process creates a version pull request when the repository uses one. Do
not use Changelogen to publish, push, or create release tags.

Review the version, changelog section, package list, and dist-tag. Merge only
after required checks pass.

## Certify and approve

Merge the reviewed version pull request. Successful `main` CI retains the exact
release candidate. Preflight then starts automatically or by a version-only
dispatch, according to the repository's Core workflow.

Preflight derives every other release value from the retained manifest. If no
release needs work, it finishes without requesting approval.

Review the pre-approval summary or release card. Approve the protected `npm`
environment. The publication job consumes the same retained candidate and does
not rebuild it.

## Verify publication

Confirm:

- every expected package version exists on npm,
- each stable package version uses `latest`,
- each prerelease package version uses `next`,
- the public SHA-1 matches the certified tarball,
- npm provenance binds those bytes to the exact repository, source commit, and
  trusted workflow identity,
- the package README renders correctly,
- the Git tag points to the release commit, and
- the GitHub release contains the exact changelog section, and
- at least one GitHub Release `.tgz` asset has the same SHA-512 as npm.

Install the package in a clean temporary consumer when package boundaries or
runtime behavior changed.

## Recover an older incomplete release

Start reconciliation with the same reviewed version, or without input when the
repository has Automatic Reconciliation. Follow only the exact maintainer
action that the workflow reports. Never infer a historical tag from a version
number or changelog alone.

The [Lazy Maintainer release standard]($docs/standards/lazy-maintainer-releases)
defines the required proof, historical-tag command, and safe retry behavior.
