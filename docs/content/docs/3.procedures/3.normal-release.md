Use the repository's release workflow after the first npm bootstrap.

## Prepare the change

Use Conventional Commits where the repository requires them. Record release
intent with the repository's selected profile:

- a single-package library uses a reviewed release note and Changelogen;
- a fixed-version package set uses Changesets; and
- an independent package family uses its documented package-family process.

Update public documentation in the same pull request. Run `pnpm verify` before
handoff.

## Prepare the version

Use the repository's protected version process. A single-package repository
can use Changelogen to update its version and `CHANGELOG.md`. A fixed-version
package set uses Changesets to update every package version and package
changelog. An independent package family follows its local compatibility and
version rules.

The process creates a version pull request when the repository uses one. Do
not use Changelogen to publish, push, or create release tags.

Review the version, changelog section, package list, and dist-tag. Merge only
after required checks pass.

## Certify and approve

Merge the reviewed version pull request. The successful `main` CI run retains
the exact release candidate and starts release preflight for its own commit.

Preflight derives the versions, package set, channel, source commit, CI run, and
tarball digests from the retained release manifest. It does not accept typed
release coordinates. If no release needs work, it finishes without requesting
approval.

Review the release card when preflight reports `AWAITING APPROVAL`. Approve the
protected `npm` environment. The publication job consumes the same retained
candidate and does not rebuild it.

## Verify publication

Confirm:

- every expected package version exists on npm,
- each stable package version uses `latest`,
- each prerelease package version uses `next`,
- the public SHA-1 matches the certified tarball,
- npm displays provenance,
- the package README renders correctly,
- the Git tag points to the release commit, and
- the GitHub release contains the exact changelog section.

Install the package in a clean temporary consumer when package boundaries or
runtime behavior changed.

## Recover an older incomplete release

Use the input-free reconcile workflow first. Do not create a tag from a
workstation based only on a version number or changelog.

The workflow can request a maintainer-created tag only when verified npm
provenance, npm integrity, retained CI evidence, and the changelog all identify
the same historical commit. Run only the exact command in the workflow summary.
Read the tag back and confirm its full target SHA before you rerun the failed
GitHub Release job.

Do not add a personal access token to automate this exceptional step. Do not
move an existing tag. A missing or conflicting fact stops recovery.

If publication stops after permanent npm state exists, use the input-free
reconcile operation. It finds the one incomplete retained candidate and
continues only when public bytes match. Follow the
[Lazy Maintainer release standard]($docs/standards/lazy-maintainer-releases)
for the complete state and recovery contract.
