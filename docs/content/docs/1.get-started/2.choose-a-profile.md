---
title: Choose a repository profile
description: Select the smallest Lupinum starter that fits the product.
icon: lucide:git-branch
---

Choose a profile from the number of independently consumed packages and from
the need for deployment. Do not create a new profile for each framework.

## Single-package library

Use the single-package library when one repository publishes one npm package.
Keep package source at the repository root. Keep the documentation app in
`docs/`.

This profile fits a Nuxt module, Vue library, or framework-neutral package that
has one release version.

## Fixed-version package set

Use the package monorepo when one product publishes two or more packages. Keep
published packages in `packages/`. Keep the documentation app in `docs/`.

Use Changesets when the packages form one product, use one version, and are
tested and released together. One reviewed Changeset records the release
intent. The protected version process consumes the Changesets and opens the
version pull request.

## Independent package family

Use an independent package family only when one repository must own related
packages that consumers can upgrade separately. Keep the package versions and
release intent independent. State which packages must remain compatible in the
repository's `MAINTAINING.md`.

This profile needs a repository-owned release process. It must certify the
complete supported package family and derive each package's release channel
from that package's version. Do not force an independent family into the
fixed-version Changesets profile.

## Deployed app

Use the deployed-app profile when the repository deploys a product but does not
publish an npm package. Do not add npm publication files to this profile.

The app still needs CI, dependency controls, security reporting, deployment
checks, a rollback procedure, and agent-readable maintenance instructions.

## Decision table

| Product | Profile |
|---|---|
| One published package with docs | Single-package library |
| Several packages released at one fixed version | Fixed-version package set |
| Related packages with independent versions | Independent package family |
| Website or service with no public package | Deployed app |
| One package plus examples | Single-package library |
| Several unrelated packages | Separate repositories unless shared ownership is necessary |

## Do not force visual symmetry

The public and operational surfaces must be consistent. Source trees need only
follow the selected profile and the framework's normal structure. Do not move
working source code only to make two repositories look alike.
