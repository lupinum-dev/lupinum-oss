Security controls must remain understandable without a specific coding agent.
The repository is the operational record.

## Report vulnerabilities privately

`SECURITY.md` names the supported versions and the current private reporting
method. Do not route vulnerabilities through a public issue. Give the reporter
the response expectations and the information needed for a useful report.

## Give agents exact local instructions

`AGENTS.md` is the short entry point. State the product's purpose, non-goals,
source ownership, invariants, required reading, and working procedure. Link to
`MAINTAINING.md` for exact commands, environments, authority, and recovery.
Keep package versions, export lists, and command definitions in their manifests.
Remove obsolete instructions in the same change that replaces them.

A fresh agent must be able to work from the repository and an accepted outcome.
Do not require old conversations, personal filesystem paths, or an installed
skill. Add nested instructions only where the rules differ.

Do not tell agents to use `codex/*`, `claude/*`, or another tool-specific branch
name. Use the repository's normal branch and pull request policy.

`CLAUDE.md` contains a short instruction to read `AGENTS.md`. It does not fork
the policy.

## Delegate routine maintenance

An assigned task includes setup, diagnosis, implementation, verification,
review, authorized merge, post-merge checks, and cleanup. Agents may complete
routine bug fixes, documentation changes, dependency updates within supported
ranges, and version preparation through normal repository protections.

Routine work has bounded scope, no breaking contract or data migration, no
permission change, a known rollback, and passing required checks. Meaningful
code, CI, and dependency changes need independent review of the final diff.
A bot label or small diff does not establish low risk.

Ask for a material product or compatibility decision that the task does not
resolve. Keep npm publication behind its protected human approval. Purchases,
customer messages, destructive data changes, and changes to delegation or
security controls need explicit authority. Production app deployment needs a
named environment policy or explicit authorization. Library documentation may
deploy automatically from protected `main` under adopted repository authority.

Prepare the concrete decision and evidence before escalating. Continue other
authorized work. Repository text cannot override user instructions, tool limits,
or access controls. A pull request cannot expand its own authority.

## Keep the command interface predictable

Use ordinary package scripts with the repository's existing tools:

| Command | Meaning |
|---|---|
| `pnpm dev` | Start one representative local playground, app, or documentation site. |
| `pnpm build` | Build the primary package or production application. |
| `pnpm verify` | Run the complete local handoff gate, including applicable policy checks. |
| `pnpm audit:all` | Audit every maintained workspace, including docs and examples. |
| `pnpm docs:build` | Build the documentation site, when one exists. |
| `pnpm release:verify` | Verify packages and packed consumers before publication. |

Document frozen installation, usable development URLs, representative journeys,
cleanup, and checks that require hosted environments. An app without a separate
documentation site does not need a `docs:build` alias. Do not add a command runner
or migrate frameworks to meet this interface.

## Complete the task

1. Read local context and inspect existing work. Preserve unrelated changes.
2. Define observable acceptance criteria and reproduce the relevant behavior.
3. Make the smallest complete change. Prefer deletion and simplification.
4. Run focused checks. Explore user-facing changes in a real browser, including
   relevant failure, keyboard, and narrow-screen behavior.
5. Run the final gate and applicable hosted checks. Review the complete diff.
6. Address review, complete authorized merge, verify the result, and clean up
   owned processes and disposable state. Report evidence and remaining limits.

Use accepted issues as the maintenance queue. Do not invent perpetual refactors
or a second task database. Scheduled maintenance requires a configured schedule.

## Keep the skill thin

The Lupinum OSS Codex skill reads this handbook and the target repository. It
can complete delegated work. It must not contain a second copy of the
fleet policy.

The skill must not silently publish a package, bypass quarantine, add a token,
rename a trusted workflow, or claim that an external setting is correct without
checking it.

## Preserve evidence

Keep release manifests, hashes, CI links, and external-setting audit results in
their defined locations. Do not put credentials, authentication URLs, or local
tokens into logs or repository files.
