---
title: Release security
description: Separate certification, publication, and GitHub release creation.
icon: lucide:shield-check
---

Build a package once. Publish the same certified tarball. Do not rebuild during
the privileged publication job.

## Certification context

The certification job can check out source, install dependencies, run package
scripts, test consumers, build packages, and create tarballs. It has no npm
credential and no repository write permission.

Record the package name, version, file name, SHA-256 digest, npm SHA-1, and
expected dist-tag in a release manifest. Retain the tarballs and manifest as an
immutable CI artifact.

Preflight starts automatically from successful `main` CI or from a dispatch
that accepts only the reviewed version. It derives the source commit, CI run,
package set, tag, channel, and artifact from the retained manifest. A
maintainer must not supply those derived values or a bootstrap override.

Temporary packed-consumer workspaces must declare only the install scripts that
their dependencies require. Use `allowBuilds` for these exact packages. Do not
copy unrelated or obsolete pnpm settings into a fixture.

## Publication context

The publication job downloads only the certified artifact. It does not check
out the repository or install dependencies. It verifies the manifest and
publishes the tarball with:

```bash
npm publish package.tgz --access public --tag latest --provenance --ignore-scripts
```

Use `next` instead of `latest` for a prerelease. Use npm trusted publishing
through OIDC. Set every public package's npm publishing access to require 2FA
and disallow bypass tokens. Never add `NPM_TOKEN`.

Do not enter the protected `npm` environment for a no-op candidate. Show the
release summary before the protected job starts. Keep the required human
approval as the final publication authority.

The first version is the only exception. A maintainer may publish the exact
CI-certified tarball once before npm trust can be configured. The protected
workflow must then verify the public SHA-1, require that version to remain the
sole package version, check the dist-tag, and record the missing provenance in
the GitHub release. A different tarball or a later version without provenance
must stop the release.

npm can take several minutes to expose a new package version. Poll the registry
with one shared time budget for the complete package set. The budget must fit
inside the job timeout. Do not restart the budget for each package, and do not
sleep after the final attempt.

## GitHub release context

Create the tag and GitHub release only after npm publication succeeds. Read the
exact version section from `CHANGELOG.md`. Require at least one `.tgz` asset
whose SHA-512 matches npm integrity; the asset name is not evidence. A readable
mismatch is `FAILED`. An unreadable asset or unavailable API is `UNVERIFIED`.

The GitHub release job needs repository write permission. It does not need npm
permission.

## Reconciliation context

The normal retry uses the same retained candidate. A Core workflow retries the
same reviewed version. Automatic Reconciliation may discover one unique
incomplete candidate without input. It stops when discovery is empty or
ambiguous.

An existing npm version is safe to continue only when its public bytes match
the certified tarball. Different bytes stop the release. Create or repair the
Git tag and GitHub Release only after the complete npm release unit is correct.

## Pin Actions

Pin every GitHub Action to a full, valid commit SHA. Dependabot can propose SHA
updates. A copied but invalid SHA fails before the job starts, so verify the SHA
against the action repository before merge.
