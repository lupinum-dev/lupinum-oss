---
title: Versioned package documentation
description: Give people and coding agents one tested path from a working example to the installed package contract.
icon: lucide:book-open-check
---

Publish documentation with the package version that it describes. A consumer
must be able to use the installed package without installing a skill, opening
an account, or contacting a documentation service.

## Give the user one starting point

Show the product working and show the code that produces that result. State
its purpose, requirements and supported release channel. Provide one complete
installation example and one copyable task prompt. Keep the manual procedure
available beside the prompt.

A live example needs a readable representation of its code, configuration,
inputs and expected result. Code tabs, component props and warnings must survive
conversion to Markdown. A screenshot or empty component tag is insufficient.
Keep the executable example and displayed source together so changes cannot
leave two different recipes.

## Keep one source for each fact

Each library owns its API explanations, examples, constraints and migration
pages. Ginko Content owns conversion to agent-readable Markdown. Ginko Docs
owns its presentation and copy/read controls. Lupinum OSS owns this standard
and objective starter checks.

The package build takes a local snapshot of canonical public documentation at
the release source. Use the same generated readable output as the website.
Do not fetch the latest website during packing or maintain a second Markdown
renderer in a library. A repository that does not use Ginko can provide plain
Markdown directly, provided the same content drives its public documentation.

The repository's root `AGENTS.md` describes maintenance. The package's consumer
entry describes installation and use. Never copy maintainer authority, release
commands or workstation paths into consumer instructions.

## Ship a stable text entry

Add this entry beside the package's existing exports:

```json
{
  "exports": {
    "./agent-docs": "./dist/agent/AGENTS.md"
  }
}
```

This export resolves a text file. Do not import it as JavaScript. Keep the
entry small: package identity, task links, runtime boundaries and fallback
instructions. Put detailed recipes in linked Markdown pages under
`dist/agent/`. Record the exact package name and version in generated metadata.
The release manifest binds the packaged bytes to their source revision.

The build must produce deterministic bytes from the same inputs. Do not insert
build times, absolute directories or random identifiers. Documentation must not
enter runtime import graphs. Include its compressed size in package review and
update explicit file allowlists and size limits intentionally.

A package family shares canonical facts, but each package exposes guidance for
its own use. Keep Nuxt, Vue, server and MCP entry choices explicit. Do not make
a user read unrelated packages before completing a basic task.

## Point the application at installed docs

A dependency-local file does not guarantee automatic discovery. Add one short
pointer to the consuming application's `AGENTS.md` during explicit onboarding.
If equivalent guidance exists, keep it. Preserve all other project content and
respect nested application instructions.

```markdown
<!-- BEGIN:lupinum-library-docs -->
For directly used Lupinum packages, resolve ./agent-docs from this application's
directory and read the relevant installed pages before changing integration.
If the export is unavailable, use installed README/types and matching release
documentation. Recheck after dependency changes. Package docs describe library
behavior; this project's instructions govern architecture, style and permissions.
Do not copy API documentation into this file.
<!-- END:lupinum-library-docs -->
```

Do not write project files from package installation or development-server
hooks. A copyable prompt or explicit scaffold operation can add the pointer.
An existing block with human edits must not be silently replaced. Duplicate,
malformed or overlapping blocks require inspection rather than a full rewrite.
No consumer skill is required. Existing skills must not become a separate source
of API facts.

Resolve the export from the application workspace. A monorepo root may not have
the same package installed. Use package resolution before assuming a physical
`node_modules` path. Read only directly used packages and pages relevant to the
task. Do not load every dependency's entire documentation corpus.

## Handle updates and missing context

Updating or rolling back the package updates its documentation. The project
pointer remains unchanged. Re-read the installed entry after a dependency change
and follow that version's migration guidance.

For an older package without the entry, use its installed README and declarations
and verify any external documentation against its version. If matching guidance
cannot be found, report the specific gap. Do not treat current website content
as proof of an older API. Missing installs and unreadable package archives are
explicit failures to resolve, not permission to use another workspace's copy.

Use this onboarding prompt, replacing the task with the requested result:

```text
Implement the requested feature using the installed Lupinum packages.
Read this application's existing instructions and preserve its conventions.
Inspect package versions, resolve each directly used package's ./agent-docs,
and read the relevant setup, recipe and migration pages. For older packages,
use installed README/types and verified matching release documentation.
Implement the feature and check its dev route, production result and narrow
layout where applicable. Preserve AGENTS.md and add the short Lupinum pointer
once if no equivalent guidance exists. Do not install a consumer skill.
```

## Certify the consumer path

Use the repository's existing verification and retained-package pipeline:

- Resolve the entry from a clean installed tarball, with npm and pnpm where
  supported. Do not prove this through source-workspace aliases.
- Check package name/version, selected page inventory and content hashes.
  Reject stale output, missing pages and references that escape the package.
- Verify that locally documented routes have a local page or an explicit
  version-matched external destination. A website URL must not silently take
  an offline reader to a different release.
- Run the first complete recipe against that tarball. Check development and
  production behavior when they have different execution paths.
- Exercise complex rendered components through focused readable-output fixtures.
- Test preservation of an existing project instruction file, repeated onboarding,
  application workspace resolution, upgrade, rollback and the older-package fallback.

A passing text check proves packaging properties. It does not prove useful prose,
a correct example or successful agent discovery. Inspect those outcomes in a
bounded consumer trial. Record model/settings, input versions, observed reads,
incorrect APIs, task time and actual application behavior. Treat runner failure
separately from task failure.

## Adopt through normal releases

Update canonical docs and examples with implementation changes. Add the generated
snapshot and certification to the next appropriate package release. Keep normal
release profiles and final npm approval. This standard does not require a new
release service, shared runtime dependency or automatic candidate scanner.

Move unique consumer-skill facts into canonical pages before retiring an existing
route. Check existing consumers and record any temporary compatibility path and
its removal condition. Do not uninstall users' skills as a side effect.

A failed adoption can roll back to the prior package and remove the project
pointer. Existing runtime APIs remain governed by their own compatibility policy.
Web delivery profiles and provider routing remain defined by the
[documentation site standard]($docs/standards/documentation-sites).
