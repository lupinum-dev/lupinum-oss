title: Lazy Maintainer releases
description: Reduce a normal release to one reviewed version pull request and one protected approval.

---

The Lazy Maintainer release path removes release coordinates from human input.
The maintainer reviews release intent and approves publication. Automation owns
state discovery, certification, publication, verification, and safe recovery.

This policy standardizes evidence and maintainer actions. Each repository keeps
its own workflows and package-specific release logic.

## Use one release state

The repository reports one of these states:

| State | Meaning | Maintainer action |
|---|---|---|
| `NO RELEASE` | No reviewed version candidate needs publication. | None. |
| `VERSION REVIEW` | A version pull request contains the proposed versions and notes. | Review and merge or close the pull request. |
| `CERTIFYING` | Unprivileged CI is building and testing the exact candidate. | None. |
| `AWAITING APPROVAL` | The candidate passed preflight and waits at the protected `npm` environment. | Review the release card and approve or reject. |
| `PUBLISHING` | The protected workflow is publishing or reconciling the candidate. | None. |
| `PARTIAL FAILURE` | Some permanent release state exists, but the release is not complete. | Start the reported reconcile action. |
| `BLOCKED` | Automation found unsafe, ambiguous, or different state. | Complete the one reported corrective action. |
| `COMPLETE` | npm, provenance, tags, Releases, and changelogs agree. | None. |

Do not report `COMPLETE` only because a workflow is green. Verify every public
release record first. An expired or unavailable observation is `UNVERIFIED` in
the fleet audit.

## Review release intent

Every published version starts in a version pull request:

- A single-package library uses Changelogen to prepare its version and
  changelog.
- A fixed-version package set consumes reviewed Changesets.
- An independent package family uses its repository-owned package-family
  process.

The version pull request is the human release-intent gate. It shows the package
or release unit, versions, channel, and release notes. Merging it authorizes
certification. It does not authorize npm publication.

The version process must not prepare a second candidate while an earlier
candidate is incomplete. This rule makes automatic reconciliation
unambiguous.

## Start from successful CI

A successful `main` CI run starts release preflight for its own exact commit.
The release workflow receives the CI run and source commit from the trusted
workflow event. A maintainer does not type a version, package name, tag,
artifact run ID, or dist-tag.

Preflight downloads the retained release candidate from that CI run. It derives
the package set, versions, channel, tarball names, and digests from the release
manifest. It compares the candidate with npm, Git tags, GitHub Releases, and the
committed changelog.

If no package needs publication or reconciliation, preflight reports
`NO RELEASE`. It must finish before it requests access to the protected `npm`
environment.

## Show one release card

Before approval, write one release card to the workflow summary:

```text
RELEASE STATUS: AWAITING APPROVAL

Profile: <single-package | fixed-package-set | independent-family>
Release unit: <name>
Source SHA: <full commit SHA>
CI run: <URL>
Channel: <latest | next>

Packages:
- <name>@<version> — <tarball SHA-256>

Confirmed:
- release intent was reviewed
- the retained candidate passed exact-SHA CI
- registry and public-history preflight passed

Blocked:
- none

Next action:
Approve the protected npm environment deployment.
```

Use the same card for all states. Keep `Next action` to one instruction. Do not
make the maintainer combine several logs to identify the candidate.

## Approve one protected boundary

Only the publication job uses the protected `npm` environment and
`id-token: write`. It downloads the verified candidate. It does not check out
source, install dependencies, restore a build cache, run package scripts, or
create replacement tarballs.

The required environment reviewer is the final publication authority. Rejecting
the deployment leaves npm unchanged.

## Reconcile instead of rebuilding

A retry uses the same retained candidate:

- Publish a missing package version.
- Skip an existing version only when its registry bytes match the certified
  tarball.
- Stop when an existing version has different bytes.
- Require provenance for every non-bootstrap publication.
- Accept missing provenance only for an explicitly recorded immutable first
  version whose bytes match.
- Create or repair the Git tag and GitHub Release only after the complete npm
  release unit is correct.

Rerun the same workflow after a transient failure. After a workflow correction
reaches `main`, use the repository's input-free reconcile dispatch. It must find
one unique incomplete retained candidate. Stop when no candidate or more than
one candidate matches. Do not ask the maintainer to copy a run ID or version.

## Separate retry from historical recovery

A normal release starts from the successful CI run for the exact current
`main` commit. A retry uses the same source commit and retained release
candidate. Both paths remain automatic after the protected npm approval.

A historical recovery is different. npm can contain certified package bytes
from an older commit while the Git tag or GitHub Release is missing. The
repository's `GITHUB_TOKEN` can have `contents: write` and still fail to create
a tag at that older commit. Do not add a personal access token or weaken tag
protection to bypass this restriction.

The recovery preflight must prove all of these facts before it asks for a
maintainer action:

- npm provenance binds the package and version to one exact source commit;
- npm integrity binds the public bytes to that provenance statement;
- successful CI for that source commit retains the expected certified release
  candidate;
- the committed changelog contains the exact version;
- the expected tag is absent; and
- no conflicting GitHub Release exists.

If one fact is missing, report `BLOCKED` or `UNVERIFIED`. Do not print a tag
command.

When all facts are proven, report `PARTIAL FAILURE` and one `HUMAN-ONLY`
action. Print an exact command that creates a lightweight tag at the proven
source commit. The command must contain the repository, complete tag, and full
commit SHA. Never ask the maintainer to edit placeholders.

After the tag exists, verify that it resolves to the proven commit. Then rerun
only the repairable GitHub Release job. That job must upload the retained
certified tarball and confirm that its bytes are identical to npm. It must not
publish or rebuild the package.

## Report failure clearly

Report `PARTIAL FAILURE` when npm accepted at least one expected version but the
release is incomplete. Report `BLOCKED` for different bytes, ambiguous
candidates, missing release intent, an invalid channel, or an unverifiable
public record.

Keep permanent npm state. Do not unpublish, move a dist-tag, replace a tag, or
create a successor version automatically. Those operations need a new explicit
maintainer decision under the
[rollback procedure]($docs/procedures/rollback).

## Keep previews separate

Package previews and `/vercel` deployments are review tools. They do not create
release authority. A Vercel preview remains optional and exact-commit. It must
not become a required pull-request check.
