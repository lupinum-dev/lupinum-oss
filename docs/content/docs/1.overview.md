Lupinum maintains a set of open-source libraries with very little human time.
Agents do most of the routine work. This standard keeps that sustainable:

- **Lazy maintenance.** A maintainer reviews pull requests and clicks two
  buttons to release. Everything else is automated or delegated to agents.
- **Real security.** npm publishing cannot happen without the maintainer's
  approval, never uses a stored token, and never runs dependency code while it
  holds publish rights.
- **Minimal tooling.** A repository contains the library, its tests, its docs
  and a small amount of standard setup. Nothing else.

The governed repositories are listed in
[`fleet/libraries.json`](https://github.com/lupinum-dev/lupinum-oss/blob/main/fleet/libraries.json).

## What a standard repository looks like

```text
.changeset/          Changesets config and pending changesets
.github/workflows/
  ci.yml             lint, typecheck, test, build and pnpm audit in parallel; final job `ci`
  release.yml        Version packages PR, pack, publish, tag and GitHub release
  preview.yml        pkg.pr.new preview packages for pull requests
docs/                documentation site (Vercel deploys it through Git)
src/ or packages/    the library
AGENTS.md            one page: commands, hard rules, library principles
DECISIONS.md         dated decision log: "Dn: decision — why"
CHANGELOG.md         generated by Changesets
CONTRIBUTING.md      short
SECURITY.md          how to report, which versions get fixes
README.md, LICENSE
renovate.json, pnpm-workspace.yaml, package.json
```

Package scripts stay close to this list: `dev`, `build`, `lint`, `format`,
`typecheck`, `test`, `docs:dev`, `docs:build`, `verify` and `changeset`.
`pnpm verify` runs what CI runs, so a green local `verify` means a green CI.
The one exception is a slow suite (end-to-end tests, a build matrix) that runs
as an extra CI job; `DECISIONS.md` names it and says why.

Libraries can ship their documentation inside the npm package, so an agent
working in a consumer project reads the docs that match the installed version.
The starters include this.

There is no `MAINTAINING.md` and no procedure handbook inside a repository.
Procedures live in this handbook. Library-specific knowledge lives in
`AGENTS.md` and `DECISIONS.md`.

## The rule for tooling

A check or script is allowed only if it guards behavior that a user relies on,
or a real attack path. Process documentation is not security. See
[Adding tooling](/docs/adding-tooling) for examples.

## What this repository provides

- **This handbook.** Seven pages. Read the one you need.
- **Starters** in `starters/`. Generate a new repository that already follows
  the standard.
- **The audit.** `pnpm audit:repos` checks every governed repository through
  its files and `gh api` and reports what differs from the standard. It never
  changes anything.
- **The `lupinum-oss` agent skill** in `skill/`. It points agents at this
  handbook and the audit.

## Change the standard

Open a pull request against `lupinum-dev/lupinum-oss`. Add an entry to its
`DECISIONS.md` that says what changes and why. Update the handbook, the
starters and the audit in the same pull request. Existing repositories adopt
the change through their own normal pull requests; run the audit to find them.
